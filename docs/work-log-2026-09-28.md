- **Nguyên nhân cốt lõi**:
  1. *Cơ chế `deleteAll` của FlutterSecureStorage trên Web*: Thư viện dùng `localStorage.removeWhere` vốn có thể bị ngắt sớm hoặc lỗi trong một số browser runtime khiến các key `smart_wardrobe_vault.*` chưa được xóa sạch.
  2. *Cờ `withCredentials` khi gọi Logout*: Khi gọi `POST /auth/logout`, nếu tắt `withCredentials`, trình duyệt sẽ không gửi cookie tới backend và bỏ qua header `Set-Cookie: accessToken=; Max-Age=0` từ backend, khiến HttpOnly cookie vẫn tồn tại trong Chrome.
  3. *State Provider trong RAM*: Các provider `subscriptionOverviewProvider`, `bodyProfileProvider`, `walletProvider` trước đó không lắng nghe `authStateProvider`, nên sau khi đăng nhập tài khoản mới mà chưa refresh thì state cũ vẫn còn.
- **Thực hiện**:
  1. `lib/core/storage/web_storage_cleaner.dart` (kèm stub và web implementation `web_storage_cleaner_web.dart` qua conditional export):
     - Xây dựng cơ chế dọn dẹp Web Storage chuyên biệt (`clearWebBrowserStorage`).
     - Trực tiếp dọn sạch `web.window.localStorage.clear()`, `web.window.sessionStorage.clear()`.
     - Xóa các cookie phi-HttpOnly thông qua `web.document.cookie` với `Max-Age=0`.
  2. `lib/core/storage/secure_storage_service.dart`:
     - Bổ sung xóa đích danh từng key quan trọng (`AppConstants.tokenKey`, `AppConstants.refreshTokenKey`, `AppConstants.userProfileKey`, `user_style_prefs`, `user_color_palette`, `web_session`) trước khi gọi `deleteAll()`.
     - Gọi `clearWebBrowserStorage()` trên Web để đảm bảo không còn bất kỳ dấu vết nào của token trong LocalStorage/SessionStorage.

     - Nguyên nhân: Container `commerce-closy-dev` đã được tạo lại và cấp IP Docker mới (`172.19.0.7`), nhưng container `nginx-closy-dev` chạy từ trước đó đã cache địa chỉ IP cũ của Commerce (vốn từng trỏ vào IP của container `account-closy-dev`). Do đó, Nginx đã chuyển tiếp toàn bộ request của Commerce (`/api/v1/me/dashboard/*`, `/api/v1/me/outfits`, `/api/v1/outfits/*`, `/api/v1/posts`) sang Account service, dẫn đến lỗi 404 cho mọi API này.

  3. **Lỗi chụp cover image chỉ chụp 1 món đồ**:

  1. **Khắc phục Nginx Gateway**:
     - Khởi động lại container Nginx (`docker restart nginx-closy-dev`) để cập nhật lại bảng phân giải DNS nội bộ của Docker Compose.

## 15. Tài liệu hướng dẫn build APK (viết sau khi đã build — rút kinh nghiệm)

User yêu cầu **giải thích trước khi làm**. Đã build trước ở §14, rồi viết
tài liệu + script verify. Bài học: với thao tác phát hành (nhiều bước, sai
lệ thường khiến app chạy sai môi trường) thì **tài liệu + script kiểm tra
tự động có giá trị hơn nhiều** so với chỉ chạy lệnh rồi báo cáo.

### Bài học kỹ thuật ghi lại
- **PowerShell 5.1 mis-parse file script có ký tự non-ASCII** → lỗi
  "Missing closing '}'" dù code nhìn đúng. Script phải viết **ASCII-only**.
- **`$ErrorActionPreference = 'Stop'` dừng script khi `apksigner`/`keytool` in
  warning ra stderr** (dù lệnh thành công). Phải dùng `Continue` rồi tự đếm
  lỗi bằng biến `$fail`.
- **`keytool` in `SHA256:`, `apksigner` in `SHA-256 digest:`** — cùng giá trị
  nhưng khác format (hoa/thường + dấu `:`). Regex so khớp phải theo đúng
  nguồn.
- `flutter build apk` **không** gặp cảnh báo strip debug symbols; chỉ
  `flutter build appbundle` mới gặp. Cả hai vẫn tạo ra file hợp lệ.
- **`Select-String` KHÔNG populate `$Matches`** — biến này chỉ được set bởi
  toán tử `-match`. Dùng `Select-String 'SHA-256 digest: (\w+)'` rồi đọc
  `$Matches[1]` → luôn rỗng → so chữ ký FAIL dù build đúng. Phải lấy `.Line`
  trước rồi `-match` trên chuỗi đó.
- **Filter `app-*abi*-release.apk` chỉ match `armeabi-v7a`** (chuỗi "abi" nằm
  trong "arme**abi**"), bỏ sót `arm64-v8a` và `x86_64`. Dùng
  `-Filter 'app-*-release.apk' | Where-Object Name -ne 'app-release.apk'`.
- **`output-metadata.json` với `--split-per-abi` có NHIỀU element**, mỗi
  element một `versionCode` riêng. Lấy `elements[0]` rồi so với universal
  APK là sai. Phải lọc theo `outputFile`.
- **Hash chữ ký in ra khác format**: `keytool` in `FA:5E:...` (hoa, có dấu
  `:`), `apksigner` in `fa5e...` (thường, không dấu). Cùng giá trị, phải
  normalize cả hai.

## 16. Tách APK theo kiến trúc (--split-per-abi)

### Vì sao APK universal nặng 63 MB
Phân tích `lib/` trong APK:

| Kiến trúc | Dung lượng | Dùng trên |
|---|---|---|
| `arm64-v8a` | 19.6 MB | Máy 64-bit (đa số flagship) |
| `armeabi-v7a` | 17.4 MB | Máy 32-bit (cũ, rẻ) |
| `x86_64` | 21.1 MB | **Emulator — không dùng trên điện thoại** |

Máy thật chỉ chạy **một** kiến trúc → 21.1 MB cho `x86_64` là lãng phí.
Phần còn lại ~7.5 MB (libflutter + libapp + assets) là bắt buộc.

### Kết quả build
| File | MB | versionCode |
|---|---|---|
| `app-arm64-v8a-release.apk` | **24.7** | 2002 |
| `app-armeabi-v7a-release.apk` | 22.5 | 1002 |
| `app-x86_64-release.apk` | 26.2 | 4002 |
| `app-release.apk` (universal) | 63.3 | 2 |
| `app-release.aab` (upload Play) | 62.3 | 2 |

Giảm **61%** (63.3 → 24.7 MB) khi cài lên điện thoại. Cả 4 APK đều ký
đúng upload keystore (SHA-256 `fa5e0657…` khớp).

### versionCode khác nhau là hành vi ĐÚNG
Flutter cộng `1000 × chỉ số ABI` để các file split không đụng nhau
(tài liệu Android `configure-APK-splits`).

⚠ **Hệ quả**: cài APK split (`vc=2002`) rồi cài bản từ Play (`vc=2`) sẽ
**báo lỗi downgrade**. Phải gỡ bản APK trước. Muốn cài đè liền mạch thì
dùng bản universal (`vc=2`).

### Không ảnh hưởng Google Play
Thứ upload lên Play là `.aab`. Play tự tách cho từng máy và tự quản lý
versionCode → người dùng tải khoảng 25 MB. 3 file APK chỉ phục vụ test
nội bộ.

### Tài liệu
- `docs/Chon_APK_Guide.md` (mới) — bảng chọn file theo máy, 4 cách xác định
  kiến trúc (ADB `getprop ro.product.cpu.abi`, CPU-Z, web), cách cài, 5 lỗi
  thường gặp, giải thích versionCode `1002/2002/4002`.
- `tool/verify_release.ps1` — nâng cấp duyệt **mọi** APK trong thư mục output,
  thêm mục **2b** in bảng từng split APK (size, ABI, versionCode, đã ký).
  Chạy PASS.

## 23. Thanh filter trang Tìm kiếm cộng đồng bị tràn

### 23.1 Nguyên nhân

Toàn bộ thanh filter là **một** `Row` cao 48px bên trong `PreferredSize(56)`:

### 23.2 Cách gọn (đã hỏi và chốt Solution A)

Tách thành 2 hàng, **cả 2 hàng dùng `Expanded`** để không bao giờ tràn:

- Hàng 1 (cao 40, `kFilterRow1Height`): 3 chip phạm vi, mỗi chip trong
  `Expanded`. Chip tab thu nhỏ: padding ngang `16 → 10`, dọc `8 → 6`, font
  `13 → 12.5`; thêm `maxLines: 1` + `ellipsis`.
- Hàng 2 (cao 32, `kFilterRow2Height`): chỉ hiện khi `searchType == 'posts'`,
  3 chip loại bài, mỗi chip trong `Expanded`, bỏ `SingleChildScrollView`.
  Chip nhỏ: padding ngang `8`, dọc `4`, font `11.5`.
- Bỏ divider dọc giữa hai nhóm (không còn cần khi đã tách hàng).
- `preferredSize` **tính động**: `40 + (posts ? 32 : 0) + 1`.

Vùng bấm của mỗi chip rộng đúng 1/3 màn hình nhờ
`GestureDetector(behavior: HitTestBehavior.opaque)` + `Center`, nên vẫn dễ
bấm dù pill chỉ ôm sát chữ.

**Lưu ý về cách đo**: đã thử đo bề rộng chip bằng widget test nhưng số liệu
**không đáng tin** — `google_fonts` không tải được font trong test nên dùng font
dự phòng rộng hơn thật ~2 lần. Vì vậy quyết định dựa trên **cấu trúc**
